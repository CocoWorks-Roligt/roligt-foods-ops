Confirmed defects

Severity-ranked triage order. Each survived an adversarial verifier that traced the code end-to-end; several were reproduced by executing the repo’s own diff and posting engines. Tick a card when it’s fixed — the checkmark stays on this device.

critical data src/context/AppContext.tsx:353
1 · Reconnect with unsaved local work deletes every document other people posted meanwhile (the open P0 write-loss, root cause)
Evidence
Reconcile sets synced.current = server (the fresh server state, line 353) but then adopts the STALE local copy as UI state (lines 358-364, `setState(migrateState(local.state, ...))`, toast 'Reconnected — saving the work done on this device'). The save effect then calls saveDb(state, synced.current) (line 455), so diffState(prev=server, next=stale-local) is computed. diffRows (src/lib/sync.ts:79-81) puts every id in prev that is absent from next into `remove` — which is exactly every row other clients added since this device's copy. commitChanges executes those removes with deleteRecord (api/_lib/commit.ts:161-168) with no guard. Verified by running the real engine: server=seed+colleague's GRN/ledger line, local=seed+own batch → diff emits grns.remove=['GRN-OTHER-1'], ledger.remove=['L-OTHER-1'].
Failure scenario
Operator A's device goes dirty (offline, or one 503/timeout marks it dirty) and reloads after colleague B posted receipts. The reconcile adopts A's stale mirror, and the push deletes B's GRNs, dispatches, ledger lines (stock silently reverses) from Zoho. B's rows are gone from the base; audit rows survive as orphans. The code comment claims 'per-document upserts ... merges with whatever else was posted meanwhile instead of erasing it' — true for upserts, false for removes.
Fix
In the reconcile's unsaved branch, diff against the base the local copy was actually built from: persist the last-synced state (or its revision) in the mirror and pass that as prev to saveDb, so rows the device never knew are never emitted as removes — and implement the documented "server has moved on" branch (compare local.revision with remote.revision) to surface a conflict dialog instead of silently adopting the stale copy. Defense in depth: have diffState drop removes for ids absent from the client's recorded base, or make the commit endpoint ignore/refuse removes for rows the payload's own base cannot account for, so no client can delete rows it never saw.
critical engine src/context/AppContext.tsx:541
2 · Concurrent document-number minting corrupts ledger and silently replaces documents (no server-side arbitration)
Evidence
nextId (AppContext.tsx:534-542) advances draft.counters purely from local state; saveDb (src/lib/dbApi.ts:82-93) sends only {changes} with no revision guard; commitChanges (api/_lib/commit.ts:177-189) writes Counters.Next as a blind value with no compare-and-swap, and upserts every collection row keyed by the minted code (api/_lib/commit.ts:158). While a device is dirty the 20s reconcile poll is skipped (AppContext.tsx:411), so its counters go stale.
Failure scenario
Two operators both hold revision R (one has any unsaved edit, so its poll is skipped). Both save a GRN: each mints RFTC20260006 and LOT-20260926-006 from counters.grn=5. Both commits succeed; B's GRNs upsert finds A's row by the same App ID and REPLACES A's document (data loss), while both devices' ledger receipt lines (distinct LED-… ids, uid()) survive. Stock for the shared lot code is double-counted, two farmers' produce merge into one traceability chain, and the append-only ledger plus insert-only audits (api/_lib/commit.ts:144) make the damage permanent without manual surgery. Same collision applies to every series (batches, challans, lots) and to period resets in nextId (line 536-538).
Fix
Arbitrate minting server-side: have /api/commit require the client's base revision and reject with 409 when app_revision has moved (client then re-syncs and re-mints), or make commitChanges do a compare-and-swap on Counters.Next per touched series and reject when the stored Next implies the client based its codes on a stale counter. Independently, refuse a collection upsert that would replace an existing row whose stored Data JSON differs from the client's implied previous value (conflict, not merge), so a colliding document code can never silently overwrite a live document.
high auth api/_lib/commit.ts:83
3 · Page-scoped write gate exempts ledger, counters and audit inserts — a scoped caller can write arbitrary stock movements, reset document numbering, and forge audit rows
Evidence
Both commit gates resolve `COLLECTIONS.find((c) => c.table === change.table)`; 'ledger' and 'audits' have no CollectionSpec (src/lib/tables.ts lines 88-118 list only documents/masters), so `spec` is undefined and neither the writePermission loop (commit.ts:69) nor the page-narrowing loop (commit.ts:83) ever applies to them. The audit gate at commit.ts:119 covers removals only — audit INSERTS are ungated for every caller. `changes.counters` (commit.ts:177-189) is written verbatim with no permission gate and no monotonicity check (any value, any series). The server never stamps caller.email onto commit-path audit rows (only writeAdminAudit does, api/_lib/adminAudit.ts:35), so the actor/`role` field is client-supplied.
Failure scenario
A lab tester whose role ticks only page.quality crafts `POST /api/commit` with `{tables:[{table:'ledger',upsert:[{id:'L-x',type:'Dispatch',item:'<any item>',qtyOut:500,lot:'...',location:'...'}],remove:[]}],counters:{}}` — accepted with 200, stock is corrupted for any item without touching a gated table (the 'the day's work stops being open' narrowing claim fails exactly where integrity matters most). The same caller posts `{tables:[],counters:{GRN:1}}` — the GRN series resets and the next receipt re-issues RFTC20260001, colliding with an existing document number. Any signed-in member can also insert audit rows with a forged actor (`role:'owner@roligt.local'`) — the trail the branch calls 'the one an auditor reads' proves nothing about who acted.
Fix
In commitChanges, treat ledger/audit upserts and non-empty counters as ride-alongs: when pageScope(caller.permissions) is non-null, refuse any commit whose only table changes are ledger/audits (or that carries counters) without at least one collection change whose page the caller holds — unscoped operators keep the open day's work. Enforce monotonic counters (write only when the new Next exceeds the stored value, with a page.settings holder allowed to reset via the numbering screen). Stamp audit rows server-side with actor = caller.email, ignoring the client-supplied actor on the commit path.
high data api/commit.ts:19
4 · No optimistic concurrency: commits carry no base revision, concurrent edits to the same document are silent last-writer-wins
Evidence
The commit request body is only { changes } (api/commit.ts:14-19) and commitChanges(zoho, caller, changes) (api/_lib/commit.ts:62) never sees the caller's base revision. upsertByKey is a blind PUT on criteria App ID = value (api/_lib/zoho.ts:191-204) — no etag/conditional check anywhere. The client's diff is computed against its own synced.current (src/lib/dbApi.ts:82-83), which can be minutes stale because the 20s poll is skipped while dirty/saving (src/context/AppContext.tsx:411).
Failure scenario
Two operators open the same GRN/QC record from the same revision. First commits; second's full-row upsert overwrites the first's version with zero signal — the plant silently holds the older client's numbers while the audit trail implies both landed. Same for QC status updates racing a packing-run edit: the roll-up is lost.
Fix
Send the client's base revision in the commit body ({ changes, baseRevision }) and have commitChanges read app_revision up front and refuse with 409 (plus the fresh snapshot/revision) when it has moved, so the client re-reads, re-diffs against the new base, and surfaces a conflict instead of blind-writing. At minimum, make the revision bump a compare-and-swap and move counter minting server-side (or make counter upserts conditional increments) so two devices can never mint the same document code — that path replaces an entire document, not just a field.
medium data api/_lib/commit.ts:200
5 · Revision bump is an unchecked read-modify-write; concurrent commits can mint the same revision and hide committed data from every reader
Evidence
commitChanges reads current revision (lines 201-205) then upserts current+1 (206-211) — no check-and-set. The snapshot cache trusts revision equality (api/_lib/snapshot.ts:143-144), the client poll trusts it (src/context/AppContext.tsx:414), and the mirror fast path adopts a clean mirror when readRevision() === local.revision (AppContext.tsx:332-341).
Failure scenario
Commits A and B on different serverless instances both read current=10 before either bumps; both write 11. Every client/cached instance that already knows revision 11 (A's committer, any instance that swept after A) treats 11 as current and never re-reads: B's committed rows are invisible plant-wide until an unrelated third commit bumps to 12 — could be the next morning. No error is raised anywhere.
Fix
Make the revision bump a compare-and-set: include the just-read value in the upsert criteria (write next only if Value still equals current) and re-read-and-retry when the guarded update matches zero rows; apply the same to writeAdminAudit. Additionally, stop letting a device adopt the commit response's revision as ground truth — re-fetch /api/revision (or a snapshot) after save so two colliding committers cannot both walk around owning the same revision.
high data api/_lib/zoho.ts:69
6 · Read budget has zero headroom: a sweep is exactly 26 reads, and revision polls plus commit reads share the same per-instance Budget — on Vercel this kills commits at the function timeout
Evidence
Budget(26)/min (zoho.ts:69-70) is per ZohoClient instance; a full sweep is exactly 26 fetchAll calls (verified: 24 mapped tables + Counters + Config; api/_lib/snapshot.ts:99-114), consuming the entire minute. Every commit adds 5-7 more reads (config gate commit.ts:99, linkMaps commit.ts:122/55-60, audit-existence fetch commit.ts:137-139, revision read commit.ts:201) and each device polls /api/revision every 20s = 3 reads/min/device through the shared client. Budget.take() sleeps server-side up to 60s (zoho.ts:50) instead of failing; vercel.json sets no functions.maxDuration (default ~10s), so the function is killed mid-sleep. Budget is per-instance while the Zoho limit is global per API key — concurrent instances each spending 26+ reads multiply into the published global cap and trigger the 5-minute lock that stops the plant.
Failure scenario
Warm instance serves a poll-triggered sweep (26 reads), then an operator's GRN commit lands within the same minute: its first link-map read sleeps ~60s, the function times out, the client gets a non-503 error → 'Offline — changes held' banner. Worse for big writes: Budget(17)/min makes a first-boot seed push (measured 106 row writes) or an offline full-push (prev=null → every row) take ~5+ minutes of sleeps — impossible inside any serverless timeout, so the seed/offline catch-up can never complete from a browser.
Fix
Make Budget.take() fail fast into ZohoLockedError (which already maps to 503 + Retry-After and the client's ThrottledError retry) whenever the projected wait would exceed the function's remaining time instead of sleeping ~60s; reserve commit headroom by lowering the sweep budget (e.g. 20/min) so polls plus commit reads always fit, and set functions.maxDuration in vercel.json. For the seed/offline full push, chunk client-side into batches of roughly 15 rows per commit request with continuation so no single request needs more than a minute of write budget, and add an automatic retry timer for held changes while a device sits idle.
high data api/_lib/commit.ts:137
7 · Commit path re-reads whole Ledger and Audit Log tables; both grow without bound, so reads-per-commit grow until commits can never finish
Evidence
Every commit containing audit upserts (i.e., nearly all — every action files an audit row) fetches the entire Audit Log to build the existing-id set (commit.ts:137-139); every document edit reverses ledger lines (house convention), making ledger.remove non-empty, which fetches the entire Ledger (commit.ts:161-163). fetchAll pages at 1000 (zoho.ts:157-172), so each of these costs ceil(rows/1000) budgeted reads. tables.ts:120-124 states the ledger 'grows without limit' by design; audits likewise (one per sticker/posting).
Failure scenario
Once Audit Log passes 1000 rows (weeks of postings), every commit pays 2+ extra reads; past ~26k audit rows the existence check alone exhausts the whole 26-read budget, every commit sleeps 60s+ and dies at the function timeout — the plant can no longer post anything. Sweeps also exceed 26 once any table crosses 1000 rows, re-creating the 80s-load behavior permanently.
Fix
Stop full-table fetches on the commit path: add a criteria-scoped paged fetch to ZohoClient (the endpoint is already fetchRecordsWithCriteria) and query only the incoming audit App IDs at commit.ts:139 and only the removed ids at commit.ts:162 — or cache the audit-id set per process keyed by the revision each commit bumps. Separately, plan for the sweep: once ledger/audits pass 1000 rows the 26-read sweep invariant documented in snapshot.ts:118-124 breaks, so sweeps need paging/archival or the same criteria treatment.

Feature verdicts

What each dimension’s reviewer concluded about the feature set itself — separate from the defect list.

auth

The architecture is sound; the holes are at the invariants’ edges, not their centers.

The migration replaces main's browser-held Supabase client with a real BFF: four same-origin auth routes (start/callback/signout/session), a sealed httpOnly cookie as the browser's only credential, server-side token refresh with the re-sealed cookie forwarded on every data response, and a 26-slug page-only permission vocabulary enforced in the commit path (per-table writePermission, page-scope narrowing, per-config-key union diff) — a large, real security improvement for a plant that previously trusted the browser completely. The Users and Roles screens drive WorkOS's management API with server-resolved targets for every access-revoking action, self-removal refused, audit rows filed and revisions bumped, and a seed script that bootstraps the chicken-and-egg. From the plant-operators' point of view what is solid: sign-in/signout work as plain links, a removed colleague's session dies within a minute in the normal case, role changes propagate without reloads, and the offline queue survives a dead session. What is fragile: the narrowing promise quietly exempts the ledger, the counters and audit inserts, so the enforcement story ('the BFF is the RLS of the fork') is weakest precisely where corruption hurts most — stock quantities and document numbering; the last-admin guard on the Roles side can be walked into a full lockout by a single confused admin; and three of the strongest guarantees (org pinning, session retirement, Secure cookies) evaporate silently on single missing env vars, with no boot-time assertion naming what was lost. Audit attribution on ordinary commits is client-supplied, so the trail proves actions happened but not who did them — an auditor should be told that. For a single-org, two-dozen-user plant the read-scope looseness (any member reads everything) is probably acceptable, but the Roles screen's promise to admins ('tick pages, that is all they get') oversells what the server enforces, and that gap is the thing most worth closing next.

data

Careful happy path. Everything concurrent is unhandled — and one path actively destroys colleagues’ work.

The data layer moves the plant from a single Supabase JSONB blob to per-document Zoho Tables rows behind a credential-holding BFF, and the fundamentals are genuinely good: every doc round-trips through a Data JSON column that survives write->read byte-exact (enrichment columns are write-only analytics, so mapper drift can only bruise a report, never the ledgers), writes are business-keyed upserts that make retries non-duplicating, the audit trail is insert-only even against crafted commits, and the permission/page gating in commitChanges is a real RLS equivalent that the tests exercise thoroughly. The revision-gated snapshot cache plus the client-mirror fast path does kill the 80-second reload in the common case. What is missing is everything concurrent: there is no compare-and-set anywhere — not on documents (same-record edits are silent last-writer-wins), not on the revision counter (concurrent bumps collide and hide committed work), and worst of all the offline-reconcile path actively destroys colleagues' postings, which I proved with the repo's own diff engine and which the code comments wrongly claim is safe ('merges with whatever else was posted meanwhile instead of erasing it'). The 26-read budget is spent with zero headroom — one sweep is exactly 26 — while polls and commit reads draw from the same per-instance Budget and the Zoho limit is global per key, and the whole-table re-reads inside commitChanges (Audit Log existence check, Ledger for removes) grow without bound, so the architecture mathematically stops working as the ledger and audit trail grow past a few thousand rows. Serverless realities are unhandled: Budget sleeps of up to 60s inside functions with no configured maxDuration mean mid-commit timeouts, half-applied plants with no revision bump, and a first-boot seed push (106 writes at 17/min) that can never complete from a browser. For plant operators the net effect today: single-user, always-online operation works well; the moment two devices are busy, one goes offline, or the base grows, work is silently lost, deleted, or invisible — and all posting-rule validation (stock, QC gates) remains client-side against possibly stale mirrors, so the server accepts any internally-consistent nonsense a stale client sends. The attachment story regressed from a working bucket to session memory, which for a food-safety audit trail is a real evidence gap. Before this backend carries a production plant, it needs a base-revision precondition on commits (reject with a re-read signal instead of clobbering), a reconnection merge that never emits removes for rows the device never touched, an atomic or collision-proof revision bump, and a read plan that does not re-scan unbounded tables per commit.

engine

Two engines ship here. The TypeScript one runs the plant; the Deluge one is a GRN-and-batch demo, not an ops system.

What this branch actually ships is two engines, and only one of them runs the plant. The Zoho Tables fork backend is the real deliverable: a well-built dumb-sync BFF (idempotent upserts keyed by business keys, insert-only audits, per-table permission gates, revision-cached snapshots, 26/17-per-minute rate budgets) plus the untouched TS posting engine, which still enforces every house rule correctly — reversal-on-edit, QC transfers from the row's current status, per-UOM totals, DRAWABLE gating, pattern-based numbering with no code parsing, control samples as non-stock lines. That layer is solid and tested (235 green). What is fragile from the plant floor's point of view is that all of that enforcement lives in the browser: the server will happily accept any ledger row or deletion from any signed-in session, and nothing arbitrates document numbers between two gate clerks receiving loads at the same moment — the exact morning rush this fork's row-diff design was meant to make safe. The Deluge engine is the second deliverable, aimed at the colleague's Creator fork, and it is not deployable in good conscience: its own status vocabulary contradicts itself so extraction can never draw received produce, its GRN costing disagrees with the app on every load containing free or rejected quantity, the concurrent-mint guard that an earlier v3 had was dropped, and QC release, packing, dispatch and stock issues simply do not exist yet (the engine's own NEXT PORTS note), so even with the status bug fixed nothing produced could ever be released, packed or shipped. Until those are closed, the Creator artifact is a GRN-and-batch demo, not an ops system; the stale fnsonly snapshot in the same folder makes it easy to import the wrong one. For operators, the React app remains the only path that both works and keeps the books honest — with the caveat that its integrity now rests entirely on every client being well-behaved."}

features

A genuinely coherent planner surface — but a planner cannot fully trust the board today.

This branch ships a genuinely coherent planner surface: orders are raised by drink with a quantity per pack format, cannot be saved without a ship-by day, and dispatch is all-or-nothing against live lots; the planning board nets demand both ways exactly per the rule (packing plans commit bulk via max(owed, planned) x packVolume, extraction/melange plans supply it, Done plans count on neither side), with overdue and undated orders never hidden and orphan SKUs still visible; and the ten live reports are pure functions of the snapshot with all state in URL params, no hidden server calls, per-UOM totals everywhere, and a correct melange net-new rule (outputs minus drawn, including negative cross-unit draws). The planningView characterization tests are strong — the 440-line suite pins the netting arithmetic, week windows, orphans and serves-closed semantics precisely. But a planner cannot fully trust the board today: for weight-sold formats (malai covers — a first-class product type) the board demands 3x the bulk and pre-fills a 'Packs' plan holding kilograms, and the whole month-window machinery quietly drops any receipt, batch, run or QC record timestamped between midnight and 05:30 on the 1st of a month because four of the derivations compare ISO timestamps as strings while two sibling derivations normalize with localDay — so the production report and the dispatch report disagree about the same month. The 'Due this week' horizon is also weaker than it looks: it narrows which orders are counted but nets against the entire board with no date awareness, so a Wednesday order can read 'Covered' by a plan dated the following Thursday, and the week's bulk number can be driven by next week's plans. On the reports side, the advertised custom span is unreachable (the picker option is dead code), and every report header carries CSV/PDF list exports that reintroduce exactly the page-level export surface the user removed on 2026-09-11 — a product decision reversed in code, not by the user. Two test-shape caveats the suite silently blesses: all report fixtures use plain date keys where live writes produce ISO timestamps (so the timezone bug is unpinnable by the current tests), and no weight-sold pack product appears in any planning test, so the kg-times-packVolume error has no coverage; also note the production report's window-level 'average yield' is an unweighted mean of monthly means, documented in-code but a number a founder could misread across a quarter. Monday morning verdict: for the litre-and-BiB core the planner can see true demand, net it, and raise the right linked plans in two clicks — but malai lines must be checked by hand, month-boundary nights and the week horizon deserve suspicion, and the reports are month-only until the custom-span control is fixed.

shell

A better shell: instant boot, page-shaped permissions, the right offline architecture — fragile exactly at the boot seams.

From the plant floor's point of view this branch delivers a genuinely better shell: the app paints instantly from the device mirror instead of a minute-long loading screen, permissions are finally page-shaped (an admin composes a lab-tech or suppliers-clerk role by ticking pages, and the nav, routes and server all obey the same list), and the offline story — local mirror, held changes, one honest save indicator — is the right architecture for a cold room with bad wifi. The restyle is coherent and disciplined: one brand ink, tabular numerals everywhere, self-hosted fonts (both subsets, rupee sign included) that load from the precache, print rules intact, and a metric-strip that folds properly on phones; it is deliberately light-only, which is fine for a shed. The fragile part is the seams of the new boot path. The mirrored fast path paints before the server confirms the copy, and the reconcile that follows both (a) certifies the screen as 'In sync' while it is still guessing and (b) wholesale-replaces state at the exact moment an operator who was told the app is ready may already be posting — losing that entry silently. Worse, the move to a server-owned cookie session quietly broke the front door of the offline promise: reopen the installed PWA without signal and you get a login screen you cannot get past, where the previous build opened straight into your data. Session expiry also now discards half-typed forms wholesale. None of these are hard to fix — carry the pending window into reconcile, cache a last-known-good session boot record with an explicit 'unverified' state, and stash modal drafts — but until they are, the features that make this PWA valuable (offline entry, instant boot) work only while nothing goes wrong at exactly the wrong moment.

Their 44 raw findings were deduped to 44; the top 8 by severity each went to one adversarial verifier prompted to refute, defaulting to refuted when uncertain (0 fell). The remaining 36 are reported unverified — nothing was dropped silently. 1.17M subagent tokens, 540 tool calls, ~37 minutes.
