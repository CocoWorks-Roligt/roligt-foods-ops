# D1 load test — 2026-10-09, scratch only

The question the Zoho years never answered until production asked it: what does the
store do when the plant actually leans on it? Asked explicitly before the D1
cutover — "_before deploying to production only we need to do a load test with
1000 and check (do this in scratch db only)_" — and answered at full scale against
**roligt-ops-scratch** (weur), the imported production plant plus everything the
run itself wrote. Every load row was cleaned up; the census came back byte-identical.

- **Script**: `scripts/d1/load-test.ts` — repeatable (`npx tsx scripts/d1/load-test.ts
  --rows 1000 --workers 8 --sustain-secs 60`). Resolves the database **by name** and
  refuses the prod UUID even if the env names it. Drives the REAL engine modules
  (`commitChangesD1`, `readSnapshotD1`) over the REAL REST client; raw REST is used
  only for measurement and one-shot boundary probes. Credentials: wrangler's own
  d1:write OAuth token (never printed, never committed); account resolved live.
- **Log**: `/tmp/d1-load-full.log` (scratch baseline revision `61:itmdv6` at start;
  run exit 0).

## Verdict for the cutover

**Green.** At a plant 3× production's size (334 real rows + 1000 synthetic), the
store showed none of the failure classes that made Zoho painful:

- **No rate limit exists to hit.** The Zoho incident class (26 reads/min, bare-400
  bursts, plant-wide 503s) has no D1 analogue — 60 s of continuous mixed traffic
  drew zero 429s. The free-tier meter that matters is `rows_read` (linear in plant
  size, ~1 per row per snapshot), not a request budget.
- **The concurrency contract holds live.** Deliberate 8-way contention on one row
  produced exactly one winner per round and clean 409s for everyone else — the
  same 409 shape the client already adopts, not a new failure mode. Single-writer
  serialization surfaces only under races the app's expect mechanism designs in.
- **The cutover-day shapes are proven**: a 1000-statement import batch (1.6 s) and
  a full snapshot at ~1150 docs (1.6 s) both fit comfortably inside the batch and
  function limits; the 101-variable refusal confirms the engine's ceilings keep
  every statement the app sends inside the per-query bound.

Caveats, stated: scratch shares prod's region hint (weur) but is not prod's
instance; the numbers are REST RTT from this machine, so the deployed function
adds its own hop on cutover day (the runbook's rehearsal covers that). The
revision stays bumped by the run's writes — monotonic by design, and this is
scratch.

one glance in the Cloudflare dashboard settles it, and even Free covers this app
roughly 10×, so the cutover does not hinge on it.

## Incremental ladder — 2026-10-09, still scratch

The full-scale run answered "does 1000 hold?"; the follow-up ask — _do it
incremental, automated, in increments of 100, and check the timings_ — is the
growth curve underneath: not whether the top holds, but what moves on the way
up.

- **Script**: `scripts/d1/load-test-incremental.ts` — repeatable (`npx tsx
  scripts/d1/load-test-incremental.ts [--step 100] [--max 1000]`). Same rules as
  the load test: scratch resolved by name (prod UUID refused), the real engine
  modules over the real REST client, every row cleaned up, census restored
  byte-identical. Each rung adds its 100 blend documents in honest ≤16-row
  commits, makes 3 expect-threaded update-commits of one existing row (a commit
  priced at the FULL rung, not the growth band crossing under it), then samples
  the timings at that volume: revision poll (raw REST — the engine's 4 s memo
  would flatter it), point read by id (the preflight shape), and full snapshots
  with the memo broken, plus `rows_read`.
- **Log**: `/tmp/d1-load-incremental.log` (baseline revision `367:2cyi4g`;
  exit 0). Every rung: revision advanced by exactly 10 (7 add-commits + 3
  update-commits), **zero errors of any class**; integrity 1000/1000 landed,
  versions 1..4, components round-trip ok; idempotent re-send at the top
  `wrote:false`, token unchanged.

What the curve says (same caveat as the full run: REST RTT from this machine):

- **Commits don't care about volume.** add-commit p50 sat in 779–863 ms and
  update p50 in 735–816 ms from 167 to 1067 docs — no trend, just RTT noise —
  and add throughput stayed flat at 16–17.5 rows/s the whole climb. The
  preflight, guarded upsert, and assert are index point-operations, O(1) in
  table size, and the ladder shows it.
- **The heartbeat and the point read are volume-blind.** poll p50 370–417 ms and
  point read p50 366–430 ms, flat across the ladder — each reads exactly one row
  (meta for the poll, a collection+id index hit for the point read). Growth
  costs the app's hottest paths nothing.
- **The snapshot is the one honest linear path: ~1 ms and one `rows_read` per
  document.** snapshot p50 climbed 1106 → 2073 ms as the plant grew 167 → 1067
  docs (≈1.07 ms/doc), and `rows_read` rose by exactly 100 per rung (215 →
  1115; the ~48-row floor is the 26 wire SELECTs' empty-collection scans plus
  counters and meta) — the limits table's linear-cost claim, now measured at ten
  points instead of two. At production's real size (~334 docs) the cold snapshot
  sits near the rung-300 row, and only the first read after a token move pays
  it — the revision-keyed STATE memo serves every later read at that token
  without a round trip.

Two lessons from building the ladder, now pinned in its comments and fixed in
the load test too: an `expect` basis must be the wrapped `{id, data}` wire row
(the preflight unwraps `.data` for spec collections — a bare document compares
against `{}` and is refused 'changed'), and a re-run's sweep must precede its
census, or cleanup compares its baseline against an aborted run's ghost rows.

**Verdict:** the climb to 1000 is flat everywhere the app is hot (commits,
polls, point reads) and honestly linear only in the full snapshot — the path
the memo amortizes and the free-tier math already budgets. Nothing bends as the
plant grows; the cutover verdict stands.
