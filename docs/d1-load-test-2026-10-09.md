# D1 load test — 2026-10-09, scratch only

The question the Zoho years never answered until production asked it: what does the
store do when the plant actually leans on it? Asked explicitly before the D1
cutover — "_before deploying to production only we need to do a load test with
1000 and check (do this in scratch db only)_" — and answered at full scale against
**roligt-ops-scratch** (weur), the imported production plant plus everything the
run itself wrote. Every load row was cleaned up; the census came back byte-identical.

- **Script**: `scripts/d1/load-test.ts` — repeatable (`npx tsx scripts/d1/load-test.ts
  --rows 1000 --workers 8 --sustain-secs 60`). Resolves the database **by name** and
  refuses the prod UUID even if the env names it. Drives the REAL engine modules
  (`commitChangesD1`, `readSnapshotD1`) over the REAL REST client; raw REST is used
  only for measurement and one-shot boundary probes. Credentials: wrangler's own
  d1:write OAuth token (never printed, never committed); account resolved live.
- **Log**: `/tmp/d1-load-full.log` (scratch baseline revision `61:itmdv6` at start;
  run exit 0).

## Results

| Phase | Result |
| --- | --- |
| 1 volume — 1000 melange docs, honest ≤16-row commits | 63 commits in **48.0 s** (20.8 rows/s), p50 **719 ms** / p95 899 / p99 1786, **zero errors**; 1000/1000 landed; revision advanced by exactly 63; idempotent re-send: `wrote:false`, token unchanged |
| 2a one 1000-statement REST batch (the import/restore shape) | success, 1000 landed in **1644 ms** |
| 2b 101-param `IN ()` (the preflight's bound) | refused (`too many SQL variables`) — the 16-row commit ceiling keeps the app's preflight at ≤17 params, inside the limit |
| 2c full snapshot with the 1000 rows present | engine **1592 ms**; `rows_read` 1115 ≈ one read per row (index-backed; cost linear in plant size, no budget) |
| 3a disjoint — 8 workers × 10 own rows | 80/80 landed, **zero conflicts**, wall 2345 ms |
| 3b contended — 10 rounds × 8 racers on one row | **exactly 10 wins** (one per round), 70 refused 409, final version 11 / final round 10 — the `_assert_changed` CHECK held the exactly-one-writer contract under real contention |
| 3c mixed — 1 writer + 1 full-snapshot reader, 15 s | writer p50 689 ms / 21 commits, reader p50 1602 ms / 9 full snapshots, **zero errors on both sides** |
| 4 sustain — 60 s, 8 workers, polls + commits | 1216 ops = **19.8 ops/s**; poll p50 371 ms, commit p50 786 ms / p95 1112; **zero 429, zero overloaded, zero 5xx** |
| 5 integrity | 1154 LOAD rows, versions 1…11, revision +163 monotonic, **components round-trip ok** (the exact array stored is the array read back) |
| 6 cleanup | every `LOAD-*` row gone, collections back to baseline exactly, revision still ahead (monotonic by design) |

## Verdict for the cutover

**Green.** At a plant 3× production's size (334 real rows + 1000 synthetic), the
store showed none of the failure classes that made Zoho painful:

- **No rate limit exists to hit.** The Zoho incident class (26 reads/min, bare-400
  bursts, plant-wide 503s) has no D1 analogue — 60 s of continuous mixed traffic
  drew zero 429s. The free-tier meter that matters is `rows_read` (linear in plant
  size, ~1 per row per snapshot), not a request budget.
- **The concurrency contract holds live.** Deliberate 8-way contention on one row
  produced exactly one winner per round and clean 409s for everyone else — the
  same 409 shape the client already adopts, not a new failure mode. Single-writer
  serialization surfaces only under races the app's expect mechanism designs in.
- **The cutover-day shapes are proven**: a 1000-statement import batch (1.6 s) and
  a full snapshot at ~1150 docs (1.6 s) both fit comfortably inside the batch and
  function limits; the 101-variable refusal confirms the engine's ceilings keep
  every statement the app sends inside the per-query bound.

Caveats, stated: scratch shares prod's region hint (weur) but is not prod's
instance; the numbers are REST RTT from this machine, so the deployed function
adds its own hop on cutover day (the runbook's rehearsal covers that). The
revision stays bumped by the run's writes — monotonic by design, and this is
scratch.
